# 01. ai-generate 아이콘 최적화

> 작업일 2026-09-01 · 대상 `src/assets/icons/consultation-summary/ai-generate.svg`
> 기준값: [01-baseline.md](./01-baseline.md)

## 문제

28 × 28 px로 표시되는 아이콘이 **2,119,126 bytes** 였다. 단일 파일로는 JS 번들 다음으로 컸다.

파일을 열어 보니 SVG가 아니라 **PNG가 SVG 껍데기를 쓰고 있었다.**

```xml
<svg width="28" height="28" viewBox="0 0 28 28">
  <rect x="0.5" y="0.5" width="27" height="27" rx="13.5"
        fill="url(#pattern0_211_1766)" stroke="url(#paint0_linear_211_1766)"/>
  <defs>
    <pattern id="pattern0_211_1766" patternContentUnits="objectBoundingBox" width="1" height="1">
      <use xlink:href="#image0_211_1766"
           transform="matrix(0.00103444 0 0 0.00103558 -0.148593 -0.111447)"/>
    </pattern>
    <image id="image0_211_1766" width="1254" height="1254" xlink:href="data:image/png;base64,..."/>
  </defs>
</svg>
```

| 항목 | 값 |
| --- | --- |
| 표시 크기 | 28 × 28 px |
| 내장 이미지 | **1254 × 1254 PNG** (알파 없음) |
| SVG 골격 (이미지 제외) | **800 bytes** |

디자인 툴에서 래스터 이미지를 포함한 채로 export 한 것으로 보인다.

---

## 접근

껍데기는 **원형 마스크(`rx="13.5"`)와 그라디언트 테두리**를 담당하고 있었다.
껍데기를 버리고 이미지 파일로 대체하면 이 둘을 CSS로 옮겨야 해서 시각적 위험이 생긴다.

그래서 **껍데기는 유지하고 내부 이미지만 교체**했다. 사용처(`AiSummarySection.tsx`)의 코드 변경이 없다.

### 표시 영역 역산

패턴 transform 행렬에서 실제로 렌더링되는 영역을 계산했다.

```
matrix(sx 0 0 sy tx ty) = matrix(0.00103444 0 0 0.00103558 -0.148593 -0.111447)

left   = -tx / sx = 144
top    = -ty / sy = 108
width  =   1 / sx = 967
height =   1 / sy = 966
```

즉 1254 × 1254 중 **(144, 108) 위치의 967 × 966 만 화면에 나왔다.**
나머지는 다운로드되지만 보이지 않는 픽셀이었다.

## 단계별 결과

| 단계 | 크기 | 직전 대비 | 성격 |
| --- | --- | --- | --- |
| 원본 PNG | 1,588,728 B | — | 1254 × 1254 |
| **① crop** | 905,836 B | -43.0% | 안 보이는 영역 제거 (**무손실**) |
| **② resize** | 10,033 B | -98.9% | 1254px → 84px (**표시 정보량 동일**) |
| **③ palette** | **2,036 B** | -79.7% | 256색 양자화 (**유일한 손실 단계**) |

84px은 표시 크기 28px의 3배로, 고밀도 디스플레이 기준이다.

### 화질 손실 측정

③ 양자화 전후를 픽셀 단위로 비교했다.

```
채널당 평균 오차 : 0.96 / 255  (0.38%)
최대 오차        : 16 / 255
```

28px로 표시되는 그라디언트 아이콘에서 평균 0.38%는 육안 식별이 어렵다.

### base64 오버헤드

base64는 바이너리를 텍스트로 바꾸므로 항상 약 33% 커진다.
원본을 줄이자 오버헤드 자체가 함께 줄었다.

| | 바이너리 | base64 | 오버헤드 |
| --- | --- | --- | --- |
| 이전 | 1,588,728 B | 2,118,304 B | +529,576 B |
| 이후 | 2,036 B | 2,716 B | +680 B |

### WebP를 쓰지 않은 이유

WebP는 648 B로 PNG(2,036 B)보다 작았지만 **SVG `<image>` 안에서 렌더링되지 않았다.**
`href` / `xlink:href` 모두 동일했고, PNG는 정상 렌더링됐다.

차이는 1.4 KB에 불과한데 실제 브라우저 검증이 어려운 호환성 위험을 감수할 이유가 없어 PNG를 선택했다.

## ⚠️ Lighthouse 점수는 비교하지 않는다

이 변경의 Lighthouse 효과를 측정하려 했으나 **측정 편차가 너무 커서 비교가 불가능했다.**

**동일한 빌드를 3회 측정한 결과**

| 실행 | Performance | LCP | TBT |
| --- | --- | --- | --- |
| run 1 | 36 | 6,532 ms | 1,582 ms |
| run 2 | 44 | 7,360 ms | 625 ms |
| run 3 | 35 | 6,526 ms | 1,616 ms |

같은 코드인데 점수가 **35 ~ 44**, TBT가 **625 ~ 1,616 ms** 로 흔들린다.
개발 머신의 CPU 부하에 따른 편차이며, 이 폭은 이번 변경의 효과보다 크다.

또한 이 아이콘은 상담 요약 페이지에서만 쓰이므로 **측정 대상인 `/`(홈)에서는 원래도 다운로드되지 않았다.**
`/` 의 지표가 변할 이유 자체가 없다.

> **따라서 이 작업의 성과로 Lighthouse 점수 변화를 주장하지 않는다.**
> [01-baseline.md](./01-baseline.md) 의 Lighthouse 수치도 단일 측정이므로 같은 한계를 갖는다.

### 앞으로의 측정 방침

1. **1차 지표는 결정론적인 것을 쓴다** — 번들 크기, 청크 구성, 라우트별 전송량.
   빌드하면 항상 같은 값이 나오므로 편차가 없다.
2. **Lighthouse는 5회 중앙값으로 본다** — 다른 작업을 돌리지 않는 상태에서 측정한다.
3. **페이지 단위로 측정한다** — 변경한 자산이 실제로 로드되는 경로에서 재야 의미가 있다.

## 재현

변환은 `sharp` 로 일회성 실행했다. 결과물만 커밋했으므로 저장소에는 의존성이 남아 있지 않다.
다시 필요하면 `npm i -D sharp` 후 아래를 실행한다.

```js
await sharp(pngBuffer)
  .extract({ left: 144, top: 108, width: 967, height: 966 })
  .resize(84, 84)
  .png({ compressionLevel: 9, palette: true, quality: 90 })
  .toBuffer();
```
