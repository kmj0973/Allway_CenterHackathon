# 03. 배경 이미지 최적화

> 작업일 2026-09-02 · 기준값 [01-baseline.md](./01-baseline.md)

## 문제

코드 스플리팅 이후 초기 로드에서 가장 큰 것이 JS가 아니라 배경 이미지였다.

| 파일 | 크기 | 원본 해상도 | 표시 크기 | 배율 |
| --- | --- | --- | --- | --- |
| `bg-stripe.png` | 552.90 kB | 1812 x 2456 | 폭 430px (앱 최대 폭) | **약 4.2x** |
| `home-gradient-top.png` | 366.33 kB | 1300 x 1300 | 650 x 650 | 2x |
| `home-gradient-bottom.png` | 332.29 kB | 1300 x 1300 | 650 x 650 | 2x |
| **합계** | **1,251.52 kB** | | | |

같은 시점의 초기 로드 JS가 810 kB였으므로 **이미지 3장이 JS보다 컸다.**

그라데이션 2장은 단순한 방사형 글로우인데도 300 kB가 넘는다.
알파 채널이 있는 부드러운 그라데이션은 PNG로 압축이 거의 되지 않기 때문이다.

---

## 결론: 셋 다 WebP로, 표시 크기에 맞춰서

```
bg-stripe            552.90 → 26.43 kB   1290px q88   (-95.2%)
home-gradient-top    366.33 → 31.68 kB    500px q75   (-91.4%)
home-gradient-bottom 332.29 → 30.96 kB    500px q75   (-90.7%)
────────────────────────────────────────────────────────────
합계               1,251.52 → 89.07 kB                (-92.9%)
```

해상도를 어떻게 정했는지가 핵심이다. 두 이미지의 성격이 달라 기준이 다르다.

### bg-stripe — 표시 크기에 정확히 맞춘다

앱 최대 폭이 `--container-app: 430px` 이므로 3배 해상도는 **1290px** 이다.

실제 텍스처가 있는 이미지라 해상도가 화질에 직접 영향을 준다.
3배 해상도(1290px)를 기준으로 재보면 이렇다.

| 폭 | 크기 | 평균 색차 | 최대 색차 |
| --- | --- | --- | --- |
| 1200px q80 | 13.4 kB | 0.74 | **22.7** |
| **1290px q88** | **25.8 kB** | **0.58** | **9.7** |
| 1812px q88 | 58.8 kB | 0.23 | 7.3 |

1200px 는 표시 크기보다 작아 브라우저가 확대하게 되고, 그 과정에서 텍스처가 뭉개진다.
**1290px 로 맞추기만 해도 최대 색차가 절반 이하가 된다.**

### 그라데이션 — 해상도를 올려도 나아지지 않는다

내용이 순수한 블러라 고주파 성분이 없다. 그래서 해상도와 오차가 무관하다.

| 폭 | 크기 (top) | 평균 색차 |
| --- | --- | --- |
| 325px q75 | 17.1 kB | 0.62 |
| **500px q75** | **30.9 kB** | **0.58** |
| 650px q75 | 49.0 kB | 0.60 |

325px 와 650px 의 오차가 같다. 남은 0.58 은 해상도가 아니라 **WebP 인코딩 자체의 한계**다.
여유를 두고 500px 로 잡았다. 650px 로 올려도 화질은 같고 크기만 60% 늘어난다.

## 시행착오 두 가지

이 작업에서 두 번 틀렸고, 둘 다 **측정 방식의 문제**였다. 기록해 둔다.

### 1. CSS radial-gradient 로 대체하려다 되돌림

그라데이션 2장이 단순한 방사형 글로우라 CSS 로 바꾸면 0 바이트가 된다고 판단했다.
원본 픽셀을 샘플링해 값을 도출하고, 등가 SVG 를 만들어 오차를 쟀다.

```
검증 결과: 배경 합성 후 평균 색차 1.31 / 0.87  → "육안 식별 불가" 로 판단
```

**하지만 검증한 것과 배포한 것이 달랐다.**

CSS `radial-gradient` 는 크기를 생략하면 `farthest-corner` 가 기본값이다.
중심이 `50% 45%` 인 정사각형에서 반지름은 **74.3%** 가 된다.
그런데 검증용 SVG 는 `r="50%"` 로 만들었다.

| | 검증한 값 (r=50%) | 실제 적용 (r=74%) |
| --- | --- | --- |
| top | 1.31 | **4.40** |
| bottom | 0.87 | **1.80** |

실제 화면에서 배경이 다르다는 지적을 받고서야 발견했다.
크기를 명시해 r=50% 로 맞춰도 WebP(0.58)보다 나쁘다.
원본이 완벽한 원이 아니라 불규칙한 얼룩이라 단일 `radial-gradient` 로는 한계가 있다.

> **교훈**: 등가 모델로 검증할 때는 **모델이 실제 렌더링 규칙과 같은지** 먼저 확인해야 한다.
> CSS 기본값을 확인하지 않은 것이 원인이었다.

### 2. bg-stripe 를 표시 크기보다 작게 줄임

처음에 1200px 로 줄였다. 표시 폭 430px 의 2.8배라 충분하다고 봤지만,
3배 해상도 기준 **1290px 에 미달**해 확대 아티팩트가 생겼다 (최대 색차 22.7).

> **교훈**: "원본보다 훨씬 작으니 충분하다" 가 아니라
> **표시 크기 x 디바이스 픽셀 비율**을 먼저 계산해야 한다.

## 결과

### 자산 크기

| 파일 | 이전 | 이후 | 변화 |
| --- | --- | --- | --- |
| `bg-stripe` | 552.90 kB | 26.43 kB | -95.2% |
| `home-gradient-top` | 366.33 kB | 31.68 kB | -91.4% |
| `home-gradient-bottom` | 332.29 kB | 30.96 kB | -90.7% |
| **합계** | **1,251.52 kB** | **89.07 kB** | **-92.9%** |

초기 로드 JS 는 810.26 kB 로 변화 없다. 이미지는 별도 자산이라 번들에 영향이 없다.
PWA 프리캐시도 868.68 KiB 로 동일하다. 이 PNG 들은 원래 프리캐시 대상이 아니라
필요한 화면에서 개별 로드되던 자산이었다.

### 화면별 첫 전송량 (gzip 기준, 주요 자산)

| 화면 | 기준값 | 현재 | 변화 |
| --- | --- | --- | --- |
| 온보딩 `/` | 1,251.73 kB | **290.24 kB** | **-76.8%** |
| 홈 `/home` | 1,397.45 kB | **326.45 kB** | **-76.6%** |
| 상담 요약 | 2,292.74 kB | **263.80 kB** | **-88.5%** |

화상 상담이 거의 그대로인 것은 정상이다.
코드 스플리팅은 총량을 줄이는 게 아니라 **필요한 사람에게만 보내는** 기법이기 때문이다.

## 재현

변환은 `sharp` 로 일회성 실행했고 결과물만 커밋했다.
다시 필요하면 `npm i -D sharp` 후 아래를 실행한다.

```js
// bg-stripe — 표시 폭 430px x 3배
await sharp(png).resize({ width: 1290 }).webp({ quality: 88 }).toBuffer();

// 그라데이션 — 순수 블러라 해상도 무관, 여유 두고 500px
await sharp(png).resize({ width: 500 }).webp({ quality: 75 }).toBuffer();
```

원본 PNG 는 삭제했으므로 Git 히스토리에서 복원해야 한다.

```bash
git show a2bea26:src/assets/shared/home-gradient-top.png > top.png
git show a2bea26:src/assets/onboarding/bg-stripe.png > stripe.png
```
